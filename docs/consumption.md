# What a consumer can delete: the consumption note

For a verified agent harness that talks to LLM providers today with hand-written decoders. Each slice of this library lets such a harness delete a named piece of its own provider code and call a proved one. The harness keeps what is policy (what to do with a reply) and the transport; it deletes what is wire contract.
Pin the library the way the harness pins any outside library (a lock line with the revision and the hash of the spec files, `scripts/pinned-lib.py hash` writes it), after `vbm-json` is pinned to the same revision.

| slice | status | the harness function it replaces | what changes in the harness |
|---|---|---|---|
| scaffold | landed | none | the repository, gates and pins exist |
| **OpenAI response decode** (`VbmLlm.OpenAI.decode`) | landed | the reader of one non-streaming reply: choice 0, its `message`, `content`, `tool_calls` (id, name, arguments), the `finish_reason`, the served `model` | one call after the parse (`LeanJson.parseFast`, then `decode`) replaces the string-keyed reads. **Differences to port deliberately:** a malformed tool call is now a typed refusal (it was silently dropped); a missing `arguments` is a refusal (the old reader defaulted it to `{}`): normalizing an empty argument string to `{}` stays the harness's policy; an empty reply (no text, no calls) is still the harness's to reject: the decoder returns it |
| **usage accounting** (`VbmLlm.OpenAI.Usage.tokens`, `Tokens.add`) | landed | the usage reader that picks `prompt_tokens` and `cached_tokens` out of the parsed reply, and the totals | `Usage.tokens` gives fresh, cached and output counts with the arithmetic proved; **differences:** a non-natural count is refused (it read as 0), a cached count above the prompt is refused (it was not checked); weighing cached against fresh tokens stays the harness's policy |
| **finish reason** (`VbmLlm.FinishClass.ofOpenAI`) | landed | the finish-reason reader (`length` means cut off) | a total map onto `complete / truncated / callsPending / filtered / unknown`; the provider's text stays in the choice |
| **streaming fold** (`VbmLlm.OpenAI.foldEvents`, over `VbmLlm.Event`) | landed (the SSE event interface is a stub until the event splitter library is pinned) | the stream normalizer: the server-sent-event line loop, the delta fold, index-keyed tool-call merge, usage in the last frame | one fold over events replaces the delta fold and the index-keyed merge (the splitting of lines into events stays the consumer's until the splitter library is pinned: events with joined `data` lines, comments dropped); **differences to port deliberately:** a stream with no sentinel is `truncated` (it was accepted silently: a consumer that wants to accept a finished stream without the sentinel reads the partial reply's `finish_reason`); an `error` chunk stops the fold and returns the message **and** the partial reply (it discarded all content: discarding is now the consumer's call); a tool-call fragment with no `index` is refused (it read as 0: `Policy.missingIndexIsZero` restores it); a tool call's `name` is the first one seen (it was concatenated); the single-shot reply the fold yields is the same type `decode` returns, so one reply reader serves both |
| **error taxonomy** (`VbmLlm.ErrorClass.ofStatus`) and **the body of a failed call** (`VbmLlm.OpenAI.decodeApiError`) | landed | the function that maps the HTTP status of a failed call to a failure class (401 and 403 credentials, 402 quota, 408 timeout, 429 rate limit, the two TLS statuses invalid, any other server error overloaded, a client error invalid or a context overflow) | one total map with the arithmetic of the statuses proved; **the words that mean a context was too long stay the harness's** (a heuristic, never proved): it passes its verdict as `contextWords`, and `overflow` comes out only for a client error that names no class of its own and only on that verdict (a server error is never an overflow). Retry, wait and bearer-refresh decisions stay the harness's (client behaviour). The body decoder reads `{error: {message, type, param, code}}` as the schema says (a numeric `code` is refused, not coerced) for a harness that reads the provider's message from the body rather than from its transport. **Allocation:** `ofStatus` allocates nothing (an enum from a number and a flag); the body decoder is the same chain of reads as the reply decoder (one record, the strings shared) |
| **tool-call turn machine** (`VbmLlm.pair`, then `VbmLlm.OpenAI.render`) | landed | the renderer that stores a turn with tool calls and renders the next request's messages: the functions that collect the results of a turn's window, look up the answer of a call and render the blocks as messages (the window of a turn, the newest result for an id, the placeholder, the orphan as text), and the proofs that go with them (well paired, an orphan is text, an unanswered call has a placeholder, a result after its call is its answer, a reply leaves the rendered prefix as it was) | the harness keeps **its own envelope** for storing a turn and a result (the stored text of an assistant block, of a result block) and its elision of old blocks: it reads each block into an `Entry` (`text role content`, `turn content calls`, `result callId content`) and calls `render`; the library proves the pairing, the harness no longer carries it. **Differences to port deliberately:** the two shown texts (`[no result]`, `[tool result] ` + the content) are the default of `RenderPolicy`, set by the harness if it wants others; a call is `ToolCall` (`id`, `name`, `arguments`), the harness's call record with its arguments field named `arguments`; the messages come out as `RequestMessage`, so they go straight into `Request.encode`; the window ends at the next assistant entry (a text under `Role.assistant` or another turn), as before. The pairing is one pass (the harness's renderer computed the collection of a window twice per turn, once for the results and once for the rest). **Allocation (read from the generated C, `Turn.c`):** `pairFrom` has no allocation site of its own; `feed` allocates per entry the result pair, the window option and either a new window or one list cell (27 allocation sites over its branches, the dead cell reused where the compiler can); the figure that decides is allocations per turn in the consumer's footprint gate, still owed. The Anthropic shape (one user message of results) will be a second `render` over the same `pair` |
| **request codec** (`VbmLlm.OpenAI.Request.encode`, then `LeanJson.print`; `Request.decode` reads one back) | landed (encode, decode and the round trip `decode (encode r) = r`) | the request builder (`messages`, `tools`, `tool_choice`, `stream`, `stream_options`, the token limits, the sampling numbers) | one typed `Request` and one `encode` replace the string-keyed object building; the encoder is proved to write each field as its member, to leave an absent field out (never `null`) and to write a count as a plain natural, and the decoder to read back exactly what the encoder wrote (`decode (encode r) = r` whenever there is a message). The decoder is for tests, replays and servers (a consumer that only sends never calls it); it refuses a role outside system, developer, user, assistant and tool, a content that is not a string, a tool-choice word that is not listed, and any present member of the wrong type, and ignores members it does not model. **Differences to port deliberately:** an empty `tools` list is left out; `stream_options` is written only when `includeUsage` is set; message content is text only (a content-part array, an image say, is not modelled yet); the model name is passed through untouched; temperature and top_p are number lexemes (`natNumber` and `Number` build them; no float is involved). **Allocation (read from the generated C, `Request.c`):** the encoder builds one `Value` tree and copies no string (the caller's strings are shared); `encodeToolCall` makes 14 constructor allocations (list cells, pairs and value wrappers), a request adds one pair, one cell and one wrapper per present member, and `LeanJson.print` then writes the bytes once: the two passes a hand-written builder also makes (build the object, serialize it). A measurement by the consumer's footprint gate is still owed (`decode-allocation-budget`) |
| **OpenRouter's variant** (`FinishClass.ofOpenRouter`, `VbmLlm.OpenRouter.decodeApiError`, the same fold) | landed | the harness's handling of OpenRouter's deviations inside its stream normalizer and error reader: the usage frame that has choices, the repeated finish reason, the mid-stream `error` chunk with HTTP 200, the numeric error code | nothing new to call for the stream: the OpenAI fold already reads usage from any frame and stops at an error chunk (with the partial reply), so the harness deletes its OpenRouter special cases with the OpenAI ones; **differences:** `finish_reason` `error` is the class `failed` through `ofOpenRouter` (OpenAI's map calls it unknown); an error body's `code` is read as a word or a natural (OpenAI's decoder refuses a number); `native_finish_reason` is not read. The comment lines are the event splitter's. **Allocation:** nothing beyond the OpenAI fold and the body decoder (one record, the strings shared) |
| **Anthropic adapter, reply side** (`VbmLlm.Anthropic.decode`, `Usage.tokens`, `FinishClass.ofAnthropic`) | landed for the non-streaming reply, its usage and its stop reason; the request codec, the named-event stream fold and the turn shape over `pair` are next | none today (a new provider convention) | one call after the parse reads the content blocks (`text`, `tool_use` with its `input` kept as the JSON value, `thinking` and `redacted_thinking` kept so they can be sent back, any other block kept raw), the stop reason (a total map onto the same classes as OpenAI's, with a new `paused` class for `pause_turn`) and the usage **with `input_tokens` excluding the cache**: `Usage.tokens` gives fresh, cache read and cache write as separate counts and the three add up to the input the model was shown, the same record OpenAI's prompt count (which includes the cache) maps onto. **Allocation:** one record per block and per reply, the strings shared, the same chain of reads as the OpenAI decoder; a tool call's input is kept as the parsed value, so a consumer that wants its text prints it once (`LeanJson.print`) |

## Measured: what a wiring slice costs in allocations

For a consumer whose footprint gate ratchets allocations per turn. Measured with a counting allocator that wraps Lean's small-object allocator (every Lean allocation counted once), one call after one warm-up call, the cost of an empty measuring window removed, on the committed vectors (so anyone can repeat it); the consumer side is the hand-written reader it would delete (string-keyed reads of Lean's own `Json`), written as such. Host-local probe, not a gate of this repository: the claim `decode-allocation-budget` stays **open** until a consumer's own gate states a budget.

| what | the hand-written code today | this library | difference |
|---|---|---|---|
| one reply with usage and a cache count (`openai-chat/001`, 1.3 KB): the parse, the reply, the model, the finish reason, the cache counts | 252 allocations, 8,440 bytes | 271, 8,232 (`parseFast`, `decode`, `Usage.tokens`, the finish class) | **+19** allocations, -208 bytes |
| one reply with one tool call (`openai-chat/003`) | 255, 8,568 | 270, 8,088 | **+15**, -480 bytes |
| the parse alone, the same reply | 217 (Lean's `Json.parse`) | 243 (`LeanJson.parseFast`) | +26: the whole rise is the verified parser; `decode` itself (28 and 31 allocations over the parse) is cheaper than the reads it replaces (35 and 41) |
| a stream of 6 events, text in pieces and usage (`s001`), from the text | 713 (split, parse each frame, fold, read the folded reply) | 611 for the fold over events, + 97 for a simple splitter stand-in | **-102** for the fold; **-5** with the splitter counted (the splitter becomes `vbm-sse`'s) |
| a stream of 6 events, one tool call in pieces (`s002`) | 924 | 776, + 97 | **-148**; **-51** with the splitter (-5.5%) |
| one request: 4 messages (system, user, assistant with a call, a tool result) and one tool | 222 (a `Json` tree and `compress`) | 77 for `Request.encode` (the value tree), **1,261** with `LeanJson.print` | **+1,039** with the printer |
| `render` (pair and render) of a conversation of 9 entries, 3 turns, 4 calls | not measured (its input is the harness's own block type) | 67 allocations, 1,800 bytes (about 7 per entry) | an adapter would add the conversion |

What follows for a ratchet. **Reply decode: wire it** (the rise is one parser's worth, 15 to 20 per reply, below a 1% tolerance on a count near 2,800, and it deletes the four separate readers); the typed `Response` carries the served model, the finish reason and the usage, so the harness keeps no `Json` value after the decode. **Stream fold: wire it with the decode** (a fall, on text and on tool calls); until `vbm-sse` is pinned the harness keeps its own line splitter. **Request codec: do not wire it into a ratcheted path yet**: the encoder is cheap, but the printer of the pinned parser library is a specification-style printer that returns a list of bytes (about two and a half allocations per output byte: 1,184 for 486 bytes); a consumer that wants the codec now converts the value tree to its own JSON type and prints with its own printer (the encoder's proofs are about the tree), and a byte-array printer is a matter for the parser library. **Turn machine:** 7 allocations per entry in one pass; its effect on a per-depth slope is owed to the consumer's own measurement.

What the library will never delete from a harness: model names and routing, prices and budgets, retry and failover, authentication and token refresh, the transport and its timeouts, what to do when a call fails.
