# What a consumer can delete: the consumption note

For a verified agent harness that talks to LLM providers today with hand-written decoders. Each slice of this library lets such a harness delete a named piece of its own provider code and call a proved one. The harness keeps what is policy (what to do with a reply) and the transport; it deletes what is wire contract.
Pin the library the way the harness pins any outside library (a lock line with the revision and the hash of the spec files, `scripts/pinned-lib.py hash` writes it), after `vbm-json` is pinned to the same revision.

| slice | status | the harness function it replaces | what changes in the harness |
|---|---|---|---|
| scaffold | landed | none | the repository, gates and pins exist |
| **OpenAI response decode** (`VbmLlm.OpenAI.decode`) | landed | the reader of one non-streaming reply: choice 0, its `message`, `content`, `tool_calls` (id, name, arguments), the `finish_reason`, the served `model` | one call after the parse (`LeanJson.parseFast`, then `decode`) replaces the string-keyed reads. **Differences to port deliberately:** a malformed tool call is now a typed refusal (it was silently dropped); a missing `arguments` is a refusal (the old reader defaulted it to `{}`): normalizing an empty argument string to `{}` stays the harness's policy; an empty reply (no text, no calls) is still the harness's to reject: the decoder returns it |
| **usage accounting** (`VbmLlm.OpenAI.Usage.tokens`, `Tokens.add`) | landed | the usage reader that picks `prompt_tokens` and `cached_tokens` out of the parsed reply, and the totals | `Usage.tokens` gives fresh, cached and output counts with the arithmetic proved; **differences:** a non-natural count is refused (it read as 0), a cached count above the prompt is refused (it was not checked); weighing cached against fresh tokens stays the harness's policy. **The reported cost** (`Usage.cost`) is the number the provider wrote for the call (OpenRouter's `usage.cost`), kept as itself for a caller that accounts in real money: absent is `none`, a value that is not a number, or a number written with a minus sign (a `-0` too: the sign of the lexeme decides, never the value), is a typed refusal (it read as 0), and no unit, no conversion and no price table is the library's |
| **finish reason** (`VbmLlm.FinishClass.ofOpenAI`) | landed | the finish-reason reader (`length` means cut off) | a total map onto `complete / truncated / callsPending / filtered / unknown`; the provider's text stays in the choice |
| **streaming fold** (`VbmLlm.OpenAI.foldEvents`, over `VbmLlm.Event`) | landed (the SSE event interface is a stub until the event splitter library is pinned) | the stream normalizer: the server-sent-event line loop, the delta fold, index-keyed tool-call merge, usage in the last frame | one fold over events replaces the delta fold and the index-keyed merge (the splitting of lines into events stays the consumer's until the splitter library is pinned: events with joined `data` lines, comments dropped); **differences to port deliberately:** a stream with no sentinel is `truncated` (it was accepted silently: a consumer that wants to accept a finished stream without the sentinel reads the partial reply's `finish_reason`); an `error` chunk stops the fold and returns the message **and** the partial reply (it discarded all content: discarding is now the consumer's call); a tool-call fragment with no `index` is refused (it read as 0: `Policy.missingIndexIsZero` restores it); a tool call's `name` is the first one seen (it was concatenated); the single-shot reply the fold yields is the same type `decode` returns, so one reply reader serves both |
| **error taxonomy** (`VbmLlm.ErrorClass.ofStatus`) and **the body of a failed call** (`VbmLlm.OpenAI.decodeApiError`) | landed | the function that maps the HTTP status of a failed call to a failure class (401 and 403 credentials, 402 quota, 408 timeout, 429 rate limit, the two TLS statuses invalid, any other server error overloaded, a client error invalid or a context overflow) | one total map with the arithmetic of the statuses proved; **the words that mean a context was too long stay the harness's** (a heuristic, never proved): it passes its verdict as `contextWords`, and `overflow` comes out only for a client error that names no class of its own and only on that verdict (a server error is never an overflow). Retry, wait and bearer-refresh decisions stay the harness's (client behaviour). The body decoder reads `{error: {message, type, param, code}}` as the schema says (a numeric `code` is refused, not coerced) for a harness that reads the provider's message from the body rather than from its transport. **Allocation:** `ofStatus` allocates nothing (an enum from a number and a flag); the body decoder is the same chain of reads as the reply decoder (one record, the strings shared) |
| **tool-call turn machine** (`VbmLlm.pair`, then `VbmLlm.OpenAI.render`) | landed | the renderer that stores a turn with tool calls and renders the next request's messages: the functions that collect the results of a turn's window, look up the answer of a call and render the blocks as messages (the window of a turn, the newest result for an id, the placeholder, the orphan as text), and the proofs that go with them (well paired, an orphan is text, an unanswered call has a placeholder, a result after its call is its answer, a reply leaves the rendered prefix as it was) | the harness keeps **its own envelope** for storing a turn and a result (the stored text of an assistant block, of a result block) and its elision of old blocks: it reads each block into an `Entry` (`text role content`, `turn content calls`, `result callId content`) and calls `render`; the library proves the pairing, the harness no longer carries it. **Differences to port deliberately:** the two shown texts (`[no result]`, `[tool result] ` + the content) are the default of `RenderPolicy`, set by the harness if it wants others; a call is `ToolCall` (`id`, `name`, `arguments`), the harness's call record with its arguments field named `arguments`; the messages come out as `RequestMessage`, so they go straight into `Request.encode`; the window ends at the next assistant entry (a text under `Role.assistant` or another turn), as before. The pairing is one pass (the harness's renderer computed the collection of a window twice per turn, once for the results and once for the rest). **Allocation (read from the generated C, `Turn.c`):** `pairFrom` has no allocation site of its own; `feed` allocates per entry the result pair, the window option and either a new window or one list cell (27 allocation sites over its branches, the dead cell reused where the compiler can); the figure that decides is allocations per turn in the consumer's footprint gate, still owed. The Anthropic shape (one user message of results) will be a second `render` over the same `pair` |
| **request codec** (`VbmLlm.OpenAI.Request.encodeBytes` gives the body as a `ByteArray` in one call; `Request.encode` gives the `Value` tree and `Request.decode` reads one back) | landed (encode, decode and the round trip `decode (encode r) = r`) | the request builder (`messages`, `tools`, `tool_choice`, `stream`, `stream_options`, the token limits, the sampling numbers) | one typed `Request` and one `encode` replace the string-keyed object building; the encoder is proved to write each field as its member, to leave an absent field out (never `null`; the one exception is an assistant message with tool calls and no text, written with `"content": null`) and to write a count as a plain natural, and the decoder to read back exactly what the encoder wrote (`decode (encode r) = r` whenever there is a message). The decoder is for tests, replays and servers (a consumer that only sends never calls it); it refuses a role outside system, developer, user, assistant and tool, a content that is not a string, a tool-choice word that is not listed, and any present member of the wrong type, and ignores members it does not model. **Differences to port deliberately:** an empty `tools` list is left out; `stream_options` is written only when `includeUsage` is set; message content is text only, plus the one-part marked text array of the cache marker (any other content-part array, an image say, is not modelled); the model name is passed through untouched; temperature and top_p are number lexemes (`natNumber` and `Number` build them; no float is involved). **The cache marker** is the caller's: `Request.encodeWith r cacheAt` writes one message's content as `[{"type": "text", "text": <the text>, "cache_control": {"type": "ephemeral"}}]` (`markable` says which messages can carry it, `lastMarkable` gives the index of the last that can), and a named message that cannot carry it writes no marker at all rather than refusing the request. The harness deletes its own marker plumbing: the byte layout of a marked prefix, and where to put it, are `Request.encodeWith` and `lastMarkable`. **`encodeWith none` is byte for byte `encodeBytes`** (`encodeWith_none`), so a harness that marks nothing changes nothing, and the decoder reads a marked body back (`Request.decode`, `Request.markerAt`), so a recorded or replayed marked body round trips. **Allocation (read from the generated C, `Request.c`):** the encoder builds one `Value` tree and copies no string (the caller's strings are shared); `encodeToolCall` makes 14 constructor allocations (list cells, pairs and value wrappers), a request adds one pair, one cell and one wrapper per present member, and `encodeBytes` (`LeanJson.printBytes` of that tree, proved equal to the reference printer's bytes by `encodeBytes_eq`) writes the bytes straight into one buffer: no list of bytes, the two passes a hand-written builder also makes (build the object, serialize it). Measured below; a measurement by the consumer's footprint gate is still owed (`decode-allocation-budget`) |
| **OpenRouter's variant** (`FinishClass.ofOpenRouter`, `VbmLlm.OpenRouter.decodeApiError`, the same fold) | landed | the harness's handling of OpenRouter's deviations inside its stream normalizer and error reader: the usage frame that has choices, the repeated finish reason, the mid-stream `error` chunk with HTTP 200, the numeric error code | nothing new to call for the stream: the OpenAI fold already reads usage from any frame and stops at an error chunk (with the partial reply), so the harness deletes its OpenRouter special cases with the OpenAI ones; **differences:** `finish_reason` `error` is the class `failed` through `ofOpenRouter` (OpenAI's map calls it unknown); an error body's `code` is read as a word or a natural (OpenAI's decoder refuses a number); `native_finish_reason` is not read. **Reasoning and provider (read data, no policy):** the reply and the fold now keep the model's reasoning text (`Message.reasoning`: the `reasoning` member, else its alias `reasoning_content`; pieces concatenate in a stream, per choice) and the serving upstream (`Response.provider`: the top-level `provider` string, the first one seen in a stream), so the harness stops parsing the stream a second time for them; a present member of another type is refused, `reasoning_details` is not read, and the Anthropic thinking text was already kept (`Block.thinking`, `thinking_delta` merged by the fold). The comment lines are the event splitter's. **Allocation:** nothing beyond the OpenAI fold and the body decoder (one record, the strings shared) |
| **Anthropic adapter** (`VbmLlm.Anthropic.decode`, `Usage.tokens`, `FinishClass.ofAnthropic`, `Request.encode` and `decode`, `render`) | landed for the non-streaming reply, its usage and stop reason, the request codec with its round trip, the turn shape over `pair` and the named-event stream fold | none today (a new provider convention) | **Reply:** one call after the parse reads the content blocks (`text`, `tool_use` with its `input` kept as the JSON value, `thinking` and `redacted_thinking` kept so they can be sent back, any other block kept raw), the stop reason (a total map onto the same classes as OpenAI's, with a new `paused` class for `pause_turn`) and the usage **with `input_tokens` excluding the cache**: `Usage.tokens` gives fresh, cache read and cache write as separate counts and the three add up to the input the model was shown, the same record OpenAI's prompt count (which includes the cache) maps onto. **Request:** one typed `Request` (`max_tokens` required, `system` as a member, messages of typed blocks, `tools` with `input_schema`, `tool_choice`) and `encode` replace the string-keyed building, proved member by member with `decode (encode r) = r`; text content only (an image or document block, the array form of a result or of `system` is refused by the decoder, not dropped). **Turn shape:** `render` over the same `pair` as OpenAI's shows one assistant message and one user message whose first blocks are the results of the turn's calls in call order, the window's text after them, proved well paired and stable when the conversation grows by a reply; a call's recorded arguments text becomes its `input` object (`badArguments` when it is not an object: the consumer's policy), system text is shown as user text (put the system prompt in `Request.system`). **Stream:** `foldEvents` over the named events (the event splitter stays the consumer's until `vbm-sse` is pinned) yields the same `Response`; the outcomes are `complete`, `truncated` and `errorEvent` as for OpenAI's, a call's `input` is parsed from its `partial_json` pieces once at `message_stop` (pieces that do not parse refuse a complete reply and stay text in a partial one), every usage count is the last non-null one, and a block's deltas concatenate so where they split does not matter; a delta for a block that never started or an event out of order is a fault, never skipped. **Allocation:** one record per block and per reply, the strings shared, the same chain of reads as the OpenAI decoder; `render` is one pass over the segments (the call's arguments are parsed once to the input object); the request tree is as cheap as OpenAI's, and the body is `Request.encodeBytes`, the byte printer's bytes (see the measured section below) |

## Measured: what a wiring slice costs in allocations

For a consumer whose footprint gate ratchets allocations per turn. Measured with a counting allocator that wraps Lean's small-object allocator (every Lean allocation counted once), one call after one warm-up call, the cost of an empty measuring window removed, on the committed vectors (so anyone can repeat it); the consumer side is the hand-written reader it would delete (string-keyed reads of Lean's own `Json`), written as such. Host-local probe (the request rows: a counting wrapper, `-Wl,--wrap`, on `lean_alloc_small_object_core` and `lean_alloc_object`, which are the calls from compiled code; the byte printer's buffer is created and grown inside the runtime, so the counter does not see it and its 2 allocations are added by hand from the result's capacity: 256 start, 514 after one doubling), not a gate of this repository: the claim `decode-allocation-budget` stays **open** until a consumer's own gate states a budget.

| what | the hand-written code today | this library | difference |
|---|---|---|---|
| one reply with usage and a cache count (`openai-chat/001`, 1.3 KB): the parse, the reply, the model, the finish reason, the cache counts | 252 allocations, 8,440 bytes | 271, 8,232 (`parseFast`, `decode`, `Usage.tokens`, the finish class) | **+19** allocations, -208 bytes |
| one reply with one tool call (`openai-chat/003`) | 255, 8,568 | 270, 8,088 | **+15**, -480 bytes |
| the parse alone, the same reply | 217 (Lean's `Json.parse`) | 243 (`LeanJson.parseFast`) | +26: the whole rise is the verified parser; `decode` itself (28 and 31 allocations over the parse) is cheaper than the reads it replaces (35 and 41) |
| a stream of 6 events, text in pieces and usage (`s001`), from the text | 713 (split, parse each frame, fold, read the folded reply) | 611 for the fold over events, + 97 for a simple splitter stand-in | **-102** for the fold; **-5** with the splitter counted (the splitter becomes `vbm-sse`'s) |
| a stream of 6 events, one tool call in pieces (`s002`) | 924 | 776, + 97 | **-148**; **-51** with the splitter (-5.5%) |
| one request, `openai-chat-request/004` (1 message, 1 tool, 470 bytes out) | not repeated (see below) | 34 for `Request.encode` (the value tree); `encode` + `LeanJson.print` (the list printer) **1,177**; `Request.encodeBytes` **34** + 2 buffer allocations the counter cannot see = **36** | **-1,141** against the list printer |
| one request, `openai-chat-request/010` (user, assistant with 2 calls, 2 tool results, 436 bytes out) | not repeated (see below) | 69 for `Request.encode`; with the list printer **1,019**; `Request.encodeBytes` **69** + 2 buffer = **71** | **-948** against the list printer |
| `render` (pair and render) of a conversation of 9 entries, 3 turns, 4 calls | not measured (its input is the harness's own block type) | 67 allocations, 1,800 bytes (about 7 per entry) | an adapter would add the conversion |

What follows for a ratchet. **Reply decode: wire it** (the rise is one parser's worth, 15 to 20 per reply, below a 1% tolerance on a count near 2,800, and it deletes the four separate readers); the typed `Response` carries the served model, the finish reason and the usage, so the harness keeps no `Json` value after the decode. **Stream fold: wire it with the decode** (a fall, on text and on tool calls); until `vbm-sse` is pinned the harness keeps its own line splitter. **Request codec: wire `Request.encodeBytes`**: the pinned parser library now has a byte printer (`LeanJson.printBytes`, proved equal to the reference printer), and the request body costs the value tree plus the buffer (a start of 256 bytes, doubled when full: 2 or 3 allocations for these vectors), about 2.2 allocations per output byte fewer than the list printer (`LeanJson.print`, which `encodeBytes` replaces; 1,019 and 1,177 on the two vectors). The earlier row of this table (one 486-byte request, 77 for the tree and 1,261 with the list printer, so **+1,039** over a hand-written 222) was a fixture that is not in the repository and was not repeated: the hand-written side (a `Json` tree and `compress`, 222) is the consumer's own code and was not re-measured either, so the table gives no difference against it. That comparison is owed to the consumer's own gate. **Turn machine:** 7 allocations per entry in one pass; its effect on a per-depth slope is owed to the consumer's own measurement.

What the library will never delete from a harness: model names and routing, prices and budgets, retry and failover, authentication and token refresh, the transport and its timeouts, what to do when a call fails.
