# Conformance vectors

`openai-chat/NAME.json` is a reply as a server sends it (or a malformed one); `NAME.expect` is what the library makes of it: `ok` and the rendering of the decoded reply, or `error` and the refusal (its path and kind).
`lake exe vbm-llm-vectors --check` decodes every vector with the compiled library and compares; `--selftest` shows the check can fail (a tampered expectation, a missing vector); `--write` regenerates the expectations, to be **read and committed by a reviewer**.

* `001` to `004`: the response examples of `POST /chat/completions` in the pinned OpenAI document, unchanged (`docs/schemas/openai-chat.md`).
* `010` to `020`: built to exercise the policy (omitted fields, two choices, empty and truncated tool arguments, an unlisted finish reason, cached tokens, duplicate keys, a contradictory usage report).
* `021` to `023`: OpenRouter's `provider` and `reasoning` (with the ignored `reasoning_details`), the `reasoning_content` alias, `reasoning` winning over the alias.
* `100` to `123`: one refusal each (not an object, no `choices`, empty, wrong types, a custom tool call, an object where `arguments` must be a string, bad counts, a bad second element, not JSON).

`openai-chat-stream/NAME.sse` is a recorded stream (the server-sent events as sent: comment lines, CR LF, an event cut off by the end of the buffer are dropped by the checker's splitter, a stub for `vbm-sse`) and `NAME.expect` the outcome of the fold: `complete`, `truncated` (with the partial reply), `error chunk` (with its message and the partial reply) or `fault`. A stream with a `NAME.single.json` beside it must fold to a complete reply that renders exactly as the single-shot decode of that file: the stream-equals-single-shot check, on data. `s020` to `s022`: reasoning pieces under the `reasoning_content` alias (with a single-shot twin), a `provider` that is not a string, a `reasoning` that is not a string; `o004` (OpenRouter's `reasoning` and `provider`, with a twin). `s001` to `s019`: text in pieces with a usage frame, a tool call with its arguments in pieces, two interleaved calls, no sentinel (also with a finish reason), an error after content, an event after the sentinel, a missing index, comment lines and CR LF, a named event, data that is not JSON, a call with no name, nothing at all, a malformed chunk, an empty-data event and unknown fields, first id wins, multi-line data, a sentinel alone.

These are conformance and regression evidence: the expectations are the library's own rendering, read by a reviewer. They prove nothing; the ledger's claims are the proofs.

`openai-chat-request/NAME.json` is a request body (the schema's own examples, `001` to `005`, unchanged; `010` to `018` built to exercise the policy (`010` and `018`: an assistant message with calls and no text is written with `"content": null`); `100` to `120` one refusal each) and `NAME.expect` is the decode: `ok` and the **canonical encoding** of the decoded request (`Request.encodeBytes`, the byte printer's bytes of `Request.encode`, which `encodeBytes_eq` proves are `LeanJson.print`'s: members in the library's order, absent ones left out, unmodelled ones gone), or `error` and the refusal (its path starts at `reply`, which here names the root value, the request). The check also decodes the canonical encoding again, from its bytes, and requires the same text: the round trip on data. The image example (`002`) is refused: content parts are not modelled, and a message is never read with its content dropped.

`openai-chat-turn/NAME.json` is a recorded conversation as a list of entries (`{"kind":"text","role":...,"content":...}`, `{"kind":"turn","content"?:...,"calls":[{"id","name","arguments"}]}`, `{"kind":"result","id","content"}`) and `NAME.expect` the messages of the next request as `VbmLlm.OpenAI.render` shows them (the `messages` array as printed JSON), or `error` for a record that is not a list of entries. `001` to `012`: a call answered, two calls with the results recorded out of order, an unanswered call, an orphan result, a result after the next assistant entry, the newest of two results, text inside a window, two turns in a row, a stray id in a window, roles and a turn with no calls, one id in two turns, a conversation extended by a reply. The checker also checks, with a second implementation that shares no code with the library, that every rendering is well paired (an assistant message followed by one `tool` message per call, in order, with the call's id, and no other `tool` message) and that the rendering of every prefix that ends before an assistant entry is a prefix of the whole.

`anthropic-messages-request/NAME.json` is a messages request body (`001` to `003` use the documented examples of the `messages` field; `010` to `018` are built to exercise the policy: system prompt and sampling, a tool call and its result, tools and each tool choice, thinking blocks sent back, a result with an error flag and no content, a duplicate key, unmodelled members; `100` to `119` one refusal each) and `NAME.expect` is the decode: `ok` and the **canonical encoding** of the decoded request, or `error` and the refusal (its path starts at `reply`, which here names the root value, the request). As for the OpenAI requests, the check also decodes the canonical encoding again, from its bytes, and requires the same text.

`anthropic-messages-turn/NAME.json` is a recorded conversation in the same entry format as `openai-chat-turn/` (`001` to `012` are those records; `020` to `023` are built for this shape: the window's text joining the results, arguments that are not an object, two turns with a stray result, system text as user text) and `NAME.expect` is the `messages` array of the next request as `VbmLlm.Anthropic.render` shows it. The checker also checks, with a second implementation that shares no code with the library, that every rendering is well paired (an assistant message that makes calls is followed directly by a user message whose first blocks are the results of exactly those calls, in order, and no result block exists elsewhere) and that the rendering of every prefix that ends before an assistant item is a prefix of the whole.

`anthropic-messages-stream/NAME.sse` is a recorded stream in the framing of the service (named events: `event:` and `data:` lines, blank line between events) and `NAME.expect` the outcome of the fold: `complete` and the reply, `truncated` and the partial reply, `error event` with its message and the partial reply, or `fault`. A stream with a `NAME.single.json` beside it must fold to a complete reply that renders exactly as the single-shot decode of that file: the stream-equals-single-shot check, on data. `a001` to `a021`: text in pieces and a ping, text then a call whose input arrives in pieces, thinking and its signature, no `message_stop`, an error event after content, an event after `message_stop`, a delta for a block that never started, a block before `message_start`, an unknown event type, an event name that differs from the data's type, pieces that do not parse as JSON, a call with no pieces, a citations delta, cumulative usage, data that is not JSON, two interleaved blocks, a delta that does not fit its block, a block started twice, a second `message_start`, no events, a lone `message_stop`.
