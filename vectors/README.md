# Conformance vectors

`openai-chat/NAME.json` is a reply as a server sends it (or a malformed one); `NAME.expect` is what the library makes of it: `ok` and the rendering of the decoded reply, or `error` and the refusal (its path and kind).
`lake exe vbm-llm-vectors --check` decodes every vector with the compiled library and compares; `--selftest` shows the check can fail (a tampered expectation, a missing vector); `--write` regenerates the expectations, to be **read and committed by a reviewer**.

* `001` to `004`: the response examples of `POST /chat/completions` in the pinned OpenAI document, unchanged (`docs/schemas/openai-chat.md`).
* `010` to `020`: built to exercise the policy (omitted fields, two choices, empty and truncated tool arguments, an unlisted finish reason, cached tokens, duplicate keys, a contradictory usage report).
* `100` to `120`: one refusal each (not an object, no `choices`, empty, wrong types, a custom tool call, an object where `arguments` must be a string, bad counts, a bad second element, not JSON).

`openai-chat-stream/NAME.sse` is a recorded stream (the server-sent events as sent: comment lines, CR LF, an event cut off by the end of the buffer are dropped by the checker's splitter, a stub for `vbm-sse`) and `NAME.expect` the outcome of the fold: `complete`, `truncated` (with the partial reply), `error chunk` (with its message and the partial reply) or `fault`. A stream with a `NAME.single.json` beside it must fold to a complete reply that renders exactly as the single-shot decode of that file: the stream-equals-single-shot check, on data. `s001` to `s019`: text in pieces with a usage frame, a tool call with its arguments in pieces, two interleaved calls, no sentinel (also with a finish reason), an error after content, an event after the sentinel, a missing index, comment lines and CR LF, a named event, data that is not JSON, a call with no name, nothing at all, a malformed chunk, an empty-data event and unknown fields, first id wins, multi-line data, a sentinel alone.

These are conformance and regression evidence: the expectations are the library's own rendering, read by a reviewer. They prove nothing; the ledger's claims are the proofs.

`openai-chat-request/NAME.json` is a request body (the schema's own examples, `001` to `005`, unchanged; `010` to `017` built to exercise the policy; `100` to `120` one refusal each) and `NAME.expect` is the decode: `ok` and the **canonical encoding** of the decoded request (`LeanJson.print` of `Request.encode`: members in the library's order, absent ones left out, unmodelled ones gone), or `error` and the refusal (its path starts at `reply`, which here names the root value, the request). The check also decodes the canonical encoding again, from its bytes, and requires the same text: the round trip on data. The image example (`002`) is refused: content parts are not modelled, and a message is never read with its content dropped.
